# /design-review — 設計図の厳格レビュー

draw.io の `.drawio.svg` 設計図を読み、**忖度なし・厳しめ**にレビューする。
方針は `~/CLAUDE.md`（設計・コードレビューの方針）と `CLAUDE.md`（design-first / 実装はオーナーが手で書く）に従う。

## スタンス（厳守）

- **忖度・社交辞令・曖昧な褒めで終わらせない**。本質は「直すべき所を漏れなく厳しく出すこと」。
- 良い点は簡潔に挙げてよいが、レポートの主役は **欠陥・抜け漏れ・改善要求**。
- **過剰設計（over-engineering）も欠陥として扱う**。小さな対象に教科書的抽象を盛るのはアンチパターン。「足りない」だけでなく「やり過ぎ」も叩く。
- 推測で褒めない。図から読み取れない事項は「読み取れない＝伝わっていない」として指摘対象にする。

## 引数

```
/design-review [図のパス] [--mode reverse|design-first]
```
- パス省略時は `docs/design/*.drawio.svg` を対象にする（複数あれば列挙し、どれをレビューするか確認）。
- `--mode` は軸E（図⇄コードの突き合わせ）の基準を決める。省略時は図とコードの内容から自動判定し、迷えば確認する。
  - **reverse**: コードが正。図がコードを正しく・**漏れなく**写せているかを見る（リバース設計＝ステップ2向け）。コードにあって図に無い要素は**網羅漏れ**として指摘。
  - **design-first**: 図が先行（正）。未実装の図要素は「未実装」として許容し、実装が図から逸脱していれば指摘する。

## Phase 0 — 図の取り込みと構造抽出

1. 対象を特定する（省略時は `docs/` 配下を Glob）。**`.drawio.svg`（Editable SVG）と `.drawio.png`（Editable PNG）の両方**に対応する。
2. **mxGraphModel XML を抽出する**。draw.io は編集用 XML を、SVG なら `<svg>` の `content="..."` 属性に、PNG なら `tEXt`/`zTXt` チャンク（キー `mxfile`）に埋め込んでいる。以下は両対応の抽出手順（Bash / python3）:
   ```bash
   python3 - "$FILE" <<'PY'
   import sys, re, html, struct, zlib, urllib.parse, base64
   path = sys.argv[1]
   if path.endswith('.png'):
       data = open(path, 'rb').read(); pos = 8; mxfile = None
       while pos < len(data) - 8:
           length = struct.unpack('>I', data[pos:pos+4])[0]
           ctype = data[pos+4:pos+8].decode('latin1'); cdata = data[pos+8:pos+8+length]
           if ctype == 'tEXt':
               k, _, v = cdata.partition(b'\x00')
               if k == b'mxfile': mxfile = urllib.parse.unquote(v.decode('latin1'))
           elif ctype == 'zTXt':
               k, _, r = cdata.partition(b'\x00')
               if k == b'mxfile': mxfile = urllib.parse.unquote(zlib.decompress(r[1:]).decode('latin1'))
           pos += 12 + length
   else:
       s = open(path, encoding='utf-8').read()
       m = re.search(r'content="(.*?)"', s, re.S)
       mxfile = html.unescape(m.group(1)) if m else None
   if not mxfile: print("NO_EMBEDDED_XML"); sys.exit()
   for name, d in re.findall(r'<diagram[^>]*name="([^"]*)"[^>]*>(.*?)</diagram>', mxfile, re.S):
       d = d.strip()
       xml = d if '<mxGraphModel' in d else urllib.parse.unquote(zlib.decompress(base64.b64decode(d), -15).decode())
       print(f"===== ページ: {name} =====\n{xml}")
   PY
   ```
   - `<diagram>` 本文が非圧縮ならそのまま、圧縮（base64+deflate）なら展開する（上のスクリプトが両方吸収する）。
   - **埋め込み XML が無い（`NO_EMBEDDED_XML`）＝非Editable な画像**。その場合はレビューに入らず、
     「編集可能な `.drawio.svg` / `.drawio.png` で保存し直せ。構造が抽出できないと厳密なレビューは不可能」と**突き返す**。
3. 抽出XMLから以下を一覧化する（以降のレビューの根拠データ）:
   - **ノード**: id / label / geometry(x,y,width,height) / style / 親子(container)関係
   - **エッジ**: source / target / label / style（方向・点線/実線）
   - 図のタイトル・凡例・注記の有無

## Phase 1 — レビュー（軸ごとに、根拠を添えて厳しく）

各指摘は必ず **「どこが（ノード/エッジ名）」「なぜ問題か」「どう直すか」** の3点をセットで書く。

### 軸A: 意図の明確さ
- **これは何図か**（構成図/シーケンス/状態遷移/データフロー/クラス図…）が一目で分かるか。曖昧なら**真っ先に**叱る。
- 対象スコープ・読み手・前提が図から読み取れるか。タイトル/凡例/単位/注記の不足。
- 「結局この図で何を伝えたいのか」が伝わらなければ、それ自体を最大の欠陥として扱う。

### 軸B: 可読性（6軸、座標を使って実測する）
| 観点 | 判定基準 |
|---|---|
| エッジ交差数 | Phase0 の座標から線分交差を**実際に数える**（複雑図 <5、単純図 0 が目標） |
| 視覚的階層 | 主役（システム境界/中心要素）が最も目立つか |
| フロー方向の一貫性 | L→R か T→B に統一されているか（混在は減点） |
| グルーピング | 関連要素が近接・整列しているか（Gestalt 近接） |
| 線の追跡性 | 各エッジを迷わず端から端まで追えるか |
| 抽象度の一貫性 | 1枚に複数の抽象レベルが混在していないか |

### 軸C: 組み込み設計観点（RTOS / Pico 2 W 文脈）
- タスク分割の粒度・責務、優先度の妥当性。
- 並行性・共有資源（排他、競合、データ競合の有無）。
- ISR / 割り込み境界（ISR内で重い処理・ブロッキングをしていないか）。
- 初期化／終了順序、リソース確保・解放。
- タイミング（周期・デッドライン・サンプリング間隔）が図に表現されているか。
- エラー時・異常時の挙動が設計されているか。
> 注: これは趣味・訓練プロジェクト。**フェイルセーフ等の製品安全要件は対象外**。

### 軸D: クリーンアーキ / 設計原則
- **依存方向**: 層境界（kernel / app / SDK）を跨ぐ依存の向き。上位が下位の実装詳細に直接依存していないか（依存性逆転）。
- レイヤ違反（例: app が SDK を直叩きして抽象を素通り）。
- 関心の分離・単一責任・凝集度/結合度。
- 抽象への依存（インターフェース分離）。
- デザインパターンの適用が**適切か**。**そして過剰でないか**（小さな対象への不要な抽象・間接層は欠陥として指摘）。
- 命名と責務が一致しているか。

### 軸E: 図⇄コードの双方向トレーサビリティ
まず**コード側の実体を Grep/Read で洗い出す**（`src/` 配下のモジュール/ファイル、タスク・関数、`#include`/呼び出し/`extern` による依存・呼び出し関係、`cre_static_tasks` 等の登録）。
そのうえで図の要素と**双方向**に突き合わせ、差分表を作る:

| 種別 | 内容 | 既定の扱い |
|---|---|---|
| **図にあってコードに無い** | 架空・陳腐化した要素 | reverse: 誤り。design-first: 未実装として許容 |
| **コードにあって図に無い** | 描き漏れ（リバース設計で最重要） | reverse: **網羅漏れ＝Major以上**。design-first: 図の範囲外か要確認 |
| **名前不一致** | 図のラベルと実シンボル名のズレ | 常に指摘 |
| **関係の不一致** | 矢印（呼び出し/依存方向）が実コードの呼び出し・依存と食い違う | 常に指摘。方向の逆転は重大 |

- リバース設計では「コード要素のうち図に表現できた割合（カバレッジ感）」も一言添える。漏れているコード実体は具体名で列挙する。
- 乖離は必ず「図が古い / 実装が逸脱 / 描き漏れ / どちらが正か」を明示する。

### 軸F: 抜け漏れ
- 境界値・初期化/終了・並行性・タイミング・リソース解放・エラー経路など、設計上**描かれるべきなのに無い**ものを洗い出す。

## Phase 2 — レポート出力

日本語で、以下の形式。**重大度順**に並べる。

```
# 設計レビュー: {図のファイル名}

## 総評（3行以内・忖度なし）
{この図が設計レビューを通せる水準か、まず結論を言う}

## 指摘事項
### 🔴 Blocker（このままでは設計として成立しない）
- [軸X] {どこが} / {なぜ問題} / {どう直す}

### 🟠 Major（要修正）
- ...

### 🟡 Minor（改善推奨）
- ...

## 可読性スコア
| 観点 | 結果 | 目標 |
| ... 6軸の実測結果 ... |

## 図⇄コードの差分（双方向トレーサビリティ）
{適用モード（reverse / design-first）を明記}
- 図にあってコードに無い: {具体名 or なし}
- コードにあって図に無い（描き漏れ）: {具体名 or なし}
- 名前/関係の不一致: {具体 or なし}
{reverse 時はカバレッジ感を一言}

## 良い点（簡潔に）
- ...
```

指摘ゼロで終わらせない。本当に欠陥が無ければ「無い」と言い切ってよいが、その場合も**なぜ通せると判断したか**を根拠付きで示すこと。
